# Масштаб и совместимость

## Настоящие большие проекты

```sh
python3 scripts/verify-scale.py
# Например, отдельная топология:
python3 scripts/verify-scale.py --sizes 100 --shape diamonds --payload-kib 128
```

Генератор создаёт отдельные проекты под `build/scale-projects`: 50 Android-модулей
в цепочке, 100 с пересекающимися зависимостями и 200 с общим базовым модулем.
Каждый имеет Java-класс с обращением к собственному R, layout, string, integer,
Manifest metadata, consumer rules и 64 KiB несжимаемых бинарных assets. Дополнительно
создаются один SDK и отдельный Maven consumer, который зависит только от SDK.

Проверяется точный набор классов, содержимое каждого asset/layout/value, объединённый
Manifest, consumer rules и отсутствие внутренних зависимостей в POM. Отдельно создаётся
APK и проверяются реальные определения всех SDK-классов в DEX. Каждый marker также
исполняется на JVM из конечного classes.jar; проверяется его результат, включая
изменённый класс при инкрементальной сборке. Это не вызов Android API. Сценарий не запускает
все сгенерированные классы на устройстве; runtime Android-функций покрывает полный полигон.

Семь этапов каждого проекта:

1. Первая сборка с пустым кешем задач данного проекта.
2. Повтор с reused configuration cache и `mergeReleaseFatAar UP-TO-DATE`.
3. Удаление build-каталогов модулей: восстановление AAR `FROM-CACHE`, тот же SHA-256.
4. Изменение Java, ресурса и бинарного asset в листовом модуле; удаление второго asset.
   Изменяется AAR, удалённый файл исчезает; Java остальных модулей остаётся UP-TO-DATE.
5. Возврат исходных файлов: исходный SHA-256 AAR.
6. Перенос исходников в другой путь: merger `FROM-CACHE`, исходный SHA-256.
7. Публикация и сборка APK независимого Maven consumer.

JSON содержит время этапов, Gradle profile, размер/хеш артефакта и оценку памяти.
RSS измеряется суммой только процессов запущенной сборки каждые 0.5 секунды.
Это приблизительный максимум резидентной памяти, не heap: короткие пики могут
пропускаться, а общие страницы — учитываться несколько раз. Сохранены GC logs.
Дистрибутивы инструментов и внешние зависимости уже находятся в кеше; первая сборка
проекта не является измерением установки Android SDK или скачивания Gradle.
Жёсткого порога времени нет: корректность обязательна, производительность сравнивается
на одинаковой машине. Тесты топологий не доказывают поддержку любых 1000 модулей.

Отчёт: `build/reports/scale-validation/result.json` и отдельные профили каждого этапа.

## Версии

Root wrapper закреплён на Gradle 9.8.0 с SHA-256, AGP — 9.4.0. Для AGP 9.4
нижняя граница Gradle — 9.6.0, Java — 17.
[Требования AGP](https://developer.android.com/build/releases/agp-9-4-0-release-notes),
[релиз Gradle 9.8](https://docs.gradle.org/9.8.0/release-notes.html).

```sh
python3 scripts/verify-compatibility.py --gradle-version 9.6.0 --expected-jdk 17 --jdk-home /path/to/jdk17
python3 scripts/verify-compatibility.py --gradle-version 9.8.0 --expected-jdk 21 --jdk-home /path/to/jdk21
```

Скрипт использует отдельный wrapper с проверенной контрольной суммой, явно выбирает
JDK для launcher и daemon, собирает три настоящих Android-модуля и SDK, публикует его
и собирает независимое приложение. Проверяет AAR, DEX и повторное использование
configuration cache у producer и consumer. Это компактная матрица совместимости;
полный полигон запускается на текущем root wrapper.
Отчёты: `build/reports/compatibility-validation/<gradle>-jdk<major>/result.json`.

## CI

`.github/workflows/validation.yml.example` сохранён как неактивный шаблон для GitHub Actions:

- каждый push/PR: Gradle 9.6/9.8 × JDK 17/21 на Ubuntu 24.04;
- каждый push/PR: полный прогон AAR, подписи, POM/GMM, debug/R8 и устройство API 35;
- по расписанию раз в неделю и вручную: 50/100/200 модулей с профилями;
- отчёты сохраняются при успехе и ошибке; тестовые секретные ключи не загружаются.

Шаблон не активирует CI при push; workflow ещё не запускался на GitHub. Локальный прогон выполняется на macOS ARM64;
Linux CI и Windows не считаются проверенными по наличию YAML.
Локальный Android runtime подтверждается на ARM64 AVD API 35; его ABI записан
в native-device-validation/result.json.
Все четыре ABI JNI собираются и анализируются в полном полигоне, а исполнение
JNI подтверждается только на фактически использованном устройстве.

Объединённый [sources JAR](sources-validation.md) реализован и проверен отдельно,
включая кеши и стандартный Signing Plugin. Публикация самого плагина в отдельный
репозиторий отложена; для локального подключения используется includeBuild.
Эта матрица проверяет SDK-публикацию.
